[43] CHAPTER 1
[44] INTRODUCTION
[45] The Hostel Inventory Management System is a web-based application developed to digitize the procurement and stock management of hostel stores in an educational institution. It replaces manual registers, phone calls and paper quotations with a single platform that connects the central administration, the individual hostel stores and the external suppliers.
[46] The system provides three types of users: Admin (Chief Warden), Store (hostel store in-charge) and Supplier. The Admin manages hostel stores, items, categories and suppliers, opens and closes the monthly requirement window, approves store requirements, consolidates demand, compares supplier quotations, issues purchase orders and records payments. The Store user views the stock of its hostel, raises monthly requirements, tracks request history and purchase orders, and updates stock when goods are received. The Supplier registers and logs in, completes a business profile, views open requirements, submits price quotations and tracks the purchase orders received.
[47] The system reduces human error, saves time, brings transparency to supplier selection, and keeps a complete digital trail from requirement to payment. It is useful for colleges, schools and any institution that runs multiple hostel stores.
[48] CHAPTER 2
[49] OBJECTIVES
[50] To provide role-based login and access control for three user types: Admin, Store and Supplier.
[51] To support multiple sign-in methods: username and password, mobile-number OTP for suppliers (Firebase Phone Authentication with an SMS gateway fallback), and Google OAuth sign-in for admins.
[52] To maintain a centralized MySQL database for stores, suppliers, categories, items, requirements, quotations, purchase orders and payments.
[53] To let hostel stores raise monthly requirements only within an admin-controlled requirement period with a deadline.
[54] To consolidate the requirements of all hostel stores into product-wise total demand with an estimated budget.
[55] To collect supplier quotations and compare them automatically by item coverage and lowest total price (L1) so the best supplier is selected transparently.
[56] To track purchase orders, deliveries, store stock updates and supplier payments.
[57] To send automatic email reminders to store in-charges before the requirement deadline and to keep a log of every email sent.
[58] To let stores rate suppliers after delivery so that supplier performance is recorded.
[59] To provide a dashboard, search with highlighting, and printable PDF reports for decision making.
[60] To provide a responsive interface with light and dark themes and a collapsible sidebar.
[61] To expose the system functions through RESTful APIs and integrate external services (Firebase, SMS gateway, Gmail).
[62] CHAPTER 3
[63] DESCRIPTION
[64] The Hostel Inventory Management System is built as a single-page React application that communicates with a Node.js and Express REST API backed by a MySQL database. After login, each user is shown a role-specific interface.
[65] Procurement workflow. (1) The Admin opens the requirement period with a deadline. (2) Each hostel store raises its monthly requirement with items and quantities. (3) The Admin reviews and approves requirements, and the system consolidates them into product-wise demand. (4) The approved requirement is opened for quotation to suppliers. (5) Suppliers submit unit prices, transport cost and delivery days. (6) The Admin compares the quotations and awards a purchase order. (7) The supplier receives the order and dispatches goods. (8) The store confirms receipt, updates stock and rates the supplier. (9) The Admin records the payment against the purchase order.
[66] Security and access. Login is validated on the server against the Admin, Store and Supplier tables. Suppliers can log in with a one-time password sent to the registered mobile number, which expires after 10 minutes. Admins can sign in with Google using their registered email address. Sessions are kept in the browser session and cleared on logout, and every page is shown only to the role that owns it.
[67] Notifications. A background scheduler sends reminder emails to store in-charges as the requirement deadline approaches, and all emails are stored in an email log shown on the Admin dashboard.

[206] 8.2 USER AUTHENTICATION & ACCESS CONTROL
[207] 8.2.0 Purpose & Scope
[208] Provides tokenized authentication, secure credential management, and Role-Based Access Control (RBAC) across the enterprise, preventing unauthorized data modifications.
[209] 8.2.1 Functional Requirements
[210] What the module must do:
[211] A user signs in with a username and password and receives a signed JWT plus a profile (id, full_name, role).
[212] A signed-in user can change their own password; administrators can register new users.
[213] Four roles – admin, manager, operator, viewer – decide which endpoints a user may call.
[214] Each account has an active / inactive status so access can be withdrawn without deleting the record, and the last login time is stored.
[215] The browser redirects unauthenticated users to the login screen (protected routes) and handles an expired or invalid token centrally.
[216] Out of scope: self-service sign-up, social login / SSO and multi-factor authentication.
[217] 8.2.2 Non-Functional Requirements
[218] How well the module must do it (the system-wide baseline in the chapter introduction also applies):
[219] Security: passwords are stored only as bcryptjs hashes with auto-generated salts; the hash is never returned by the API.
[220] Brute-force defence: at most 15 login attempts per 15 minutes per IP address on /api/auth/login.
[221] Session length: tokens expire after 12 hours, which limits the damage of a stolen token while avoiding repeated logins in one shift.
[222] Scalability: because tokens are stateless, any server instance can validate a request without a shared session store.
[223] Latency target: login under 500 ms (dominated by the deliberate cost of bcrypt); token verification adds only microseconds per request.
[224] CAP: the user table is a single MySQL source of truth – consistency is preferred, so a disabled account is refused immediately on the next login.

[267] 8.2.5 Low-Level Architecture
[268] Fig 8.2.A Low-level architecture – USER AUTHENTICATION & ACCESS CONTROL
[269] Request flow:
[270] Login.jsx posts the credentials; rateLimiter.js counts the attempt for the caller’s IP.
[271] authController looks the user up by username (unique index), checks that the status is active, and compares the password with the stored bcrypt hash.
[272] On success it updates last_login, signs a JWT (12 h) and returns the token with the profile.
[273] The client stores the token; api.js adds it as a Bearer header on every later request.
[274] auth.js verifies the signature and expiry and checks the role before the route handler runs.
[275] A 401 response triggers the Axios interceptor, which clears the session and sends the user back to the login screen.

[305] 8.3 MASTER DATA MANAGEMENT
[306] 8.3.0 Purpose & Scope
[307] Unifies foundational reference datasets and enterprise catalogs that establish the baseline for all store operations, inventory classification, and vendor management.
[308] 8.3.1 Functional Requirements
[309] What the module must do:
[310] Create, view, edit and delete records for: Item, Supplier, Department, Store Master, Product Head, Sub Head, UOM, State, Purchase Type, Party Master and Item Master (gate-pass items).
[311] Central item catalog: item code, name, department, sub head, UOM, unit rate, opening stock, min / max stock level (reorder level), HSN code, location.
[312] Supplier registry: account name, place, address, delivery address, GSTIN, PAN, contact details and opening credit / debit.
[313] Search and filter large lists: suppliers by department, place and GST status; items by department, sub head and UOM; sorting and page size.
[314] Bulk upload of items from a CSV file.
[315] Purchase Type records carry accounting formulas (assessable value, round off, lorry freight) and SGST / CGST / IGST / TCS ledger mappings.
[316] Provide searchable reference dropdowns to every transaction screen so users pick, rather than type, master values.
[317] 8.3.2 Non-Functional Requirements
[318] How well the module must do it (the system-wide baseline in the chapter introduction also applies):
[319] Read-heavy: masters are read many times more often than they are changed (roughly 100 reads per write), so look-ups must be fast.
[320] Scale of lists: with 5,490 suppliers and 11,011 items, lists are paginated on the server (10 per page by default) and never loaded whole.
[321] Data quality: unique keys on department name, state name, store name and purchase type prevent duplicates; item and sub head records link to their parent through department_id / SubHeadCode.
[322] Access control: write endpoints are restricted by role (for example, the viewer role is read-only).
[323] CAP: consistency first – a new supplier or item must be visible to every user as soon as it is saved, because transactions depend on it immediately.

[470] 8.4 PURCHASE ORDER (PO) MANAGEMENT
[471] 8.4.0 Purpose & Scope
[472] Orchestrates the procurement lifecycle, from raising purchase orders with approved vendors to multi-item price calculations, status tracking, and authorized order cancellations.
[473] 8.4.1 Functional Requirements
[474] What the module must do:
[475] Raise a PO for a supplier: order date, party, address / place, reference number and remarks; the PO number (for example PO-772) is generated automatically in sequence.
[476] Multi-item line engine: each line takes item, quantity, unit rate, discount %, GST type (SGST + CGST or IGST), packing & forwarding, lorry freight and MRS number, and shows the line total instantly.
[477] Order summary: items subtotal, total discount, total tax, P&F, lorry freight, round off and grand total.
[478] Lifecycle tracking: Draft → Pending / Approval → Approved → Inward Created → Completed / Cancelled.
[479] Register: search by order number, party or reference; filter by party and status; sort; expand a row to see its lines; copy, edit or delete a PO.
[480] Controlled cancellation: a PO is cancelled only with a mandatory reason, and not once its items have arrived at the gate.
[481] 8.4.2 Non-Functional Requirements
[482] How well the module must do it (the system-wide baseline in the chapter introduction also applies):
[483] Accuracy: amounts are DECIMAL(15,2) and unit rates DECIMAL(15,6), so a PO total always matches the sum of its lines. Example (Fig 8.4.3–8.4.4): ₹20,000 − ₹1,800 discount = ₹18,200; GST is 18 % of (₹18,200 + ₹5,000 P&F + ₹5,000 freight) = ₹5,076; grand total = ₹18,200 + ₹5,000 + ₹5,000 + ₹5,076 = ₹33,276.
[484] Atomicity: the header and all its lines are saved together in one transaction; a PO never exists half-saved.
[485] Unique numbering: the PO number is allocated on the server and the primary key is the final guard against duplicates when two clerks save at the same time.
[486] Server-side validation: totals sent by the browser are recomputed on the server before saving.
[487] Auditability: every cancellation stores a reason and date; all tables carry createdAt / updatedAt.
[488] Responsiveness: the register opens in under 1 second; line details load only when a row is expanded.
[489] CAP: consistency first – the status of a PO must be identical for the store, accounts and management at all times.

[604] 8.5.0 Purpose & Scope

[606] 8.5.1 Functional Requirements
[607] What the module must do:
[608] Gate Inward: log an arrival with an automatic inward number (for example GI-771), inward date, party, the purchase order being delivered, and the supplier’s invoice number and date.

[884] Edit or delete an existing issue; list issues by department.
[885] Gate Pass Out / In: record tools, machinery and non-inventory goods leaving or re-entering the premises with party, items and quantities.
[886] Returnable (RGP) and non-returnable (NRGP) passes, and return reconciliation of items coming back against open passes.
[887] 8.7.2 Non-Functional Requirements
[888] How well the module must do it (the system-wide baseline in the chapter introduction also applies):
[889] Stock integrity: stock must never go negative – the quantity is validated on the server inside a transaction that locks the item rows being issued.
[890] Concurrency: two storekeepers issuing the same item at the same moment are serialized by the row lock, so the second sees the reduced balance.
[891] Usability: a department can have hundreds of items; the list is filterable and shows the remaining stock as the user types.
[892] Accountability: each issue stores the department, indent number, approver and employee name for every line.
[893] CAP: consistency first – an out-of-date stock figure would allow over-issue, so correctness outranks availability.

[1097] CONCLUSION
[1098] The Store Management System provides a complete digital solution for managing the major activities involved in store and inventory operations. The system integrates master data management, purchase orders, gate inward entries, goods receipts, bill processing, item issues, gate passes, dashboards, and reports within a single application. By replacing manual records and disconnected processes, it improves the accuracy, consistency, and accessibility of operational information. The application was developed using React for the frontend, Node.js and Express for the backend, and MySQL with Sequelize for database management. Its client-server architecture supports structured communication between the user interface, application server, and database. JWT authentication, password hashing, role-based access control, request rate limiting, and protected routes help secure the system and prevent unauthorized access. The completed project demonstrates how a web-based information system can simplify store operations, reduce repetitive work, minimize recording errors, and improve decision-making. Its modular structure makes the application easier to maintain and allows additional features to be introduced in the future. Overall, the Store Management System successfully meets its objective of providing a secure, organized, and efficient platform for managing store activities at KR Exports.
